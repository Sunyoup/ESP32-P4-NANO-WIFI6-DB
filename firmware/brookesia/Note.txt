ESP32-P4 rev3.1 + ESP-IDF 사용 시 주의사항 (Brookesia 빌드 작업 정리)

오늘 작업에서 확인한 것과 확인하지 못한 것을 나눠서 정리한다.
오늘 겪은 에러 중 rev3.1 때문이라고 확인된 것은 많지 않다.


== rev3.1과 직접 관련된 것 (확인됨) ==

1. 최소 칩 리비전 설정
 - sdkconfig에 CONFIG_ESP32P4_REV_MIN_301=y, REV_MAX_FULL=399가 들어 있다.
   이 이미지는 v3.1 이상 칩에서만 돈다.
 - rev1.x나 2.x 보드에 그대로 올리면 부팅 단계에서 거부된다.
   반대로 rev1.x용으로 빌드한 이미지는 v3.x에서 그대로 돌기도 하지만,
   리비전 범위 설정을 확인할 것.
 - 부트 로그에 "chip revision: v3.1"로 잘 나온다.

2. 리비전 의존 기능이 라이브러리에서 갈라진다
 - esp_video는 CONFIG_ESP32P4_REV_MIN_FULL >= 300일 때만 켜지는 기능이 있다
   (esp_video_caps.h:70-76). 예를 들어 YUV422 short 스왑은
   IDF 6.1 이상과 rev3.0 이상이 함께 필요하다.
 - rev3.x는 ISP/CSI 쪽 하드웨어가 바뀐 부분이 있어서, 카메라 관련 코드는
   IDF와 컴포넌트 버전을 맞춰 써야 한다.


== rev3.1과 상관없이 오늘 겪은 것 (IDF와 라이브러리 버전 문제) ==

3. IDF 스냅샷 함정 (가장 큰 함정)
 - v6.1-dev 중간 스냅샷은 버전 번호가 6.1.0이어도 CSI 에러 이벤트 API가 없었고,
   esp_video 2.5.0이 버전 번호만 보고 컴파일하다 실패했다.
   (esp_cam_ctlr_error_event_data_t, on_error 없음)
 - rev3.1 자체 문제는 아니지만, rev3.x는 최신 IDF 지원이 필요해서
   개발 스냅샷을 쓰기 쉽다.
 - 정식 릴리스(v6.1, v6.0.3 이상, v5.5.6 이상)를 쓸 것.

4. 부트로더 크기 초과 (0x6060 > 0x6000)
 - 96바이트 넘친 것이다. rev3.x 지원 코드 때문에 커졌을 가능성이 있다고
   추측했지만 확인하지는 못했다. IDF 릴리스나 옵션에 따라서도 달라질 수 있다.
 - 해결: partition table 오프셋을 0x10000으로 변경
   (CONFIG_PARTITION_TABLE_OFFSET=0x10000), partitions.csv의 factory를
   0x110000 -> 0x120000으로 이동.
 - 파티션 레이아웃이 바뀌었으니 이전 병합 바이너리(FactoryOnly-*.bin)와
   섞지 말 것. 처음 한 번은 idf.py erase-flash flash 권장 (NVS 데이터 삭제됨).


== 보드(Nano) 특유의 함정 (칩 리비전과 무관) ==

5. ESP-Hosted 핀 - 오늘 Wi-Fi가 안 된 진짜 원인
 - sdkconfig.defaults의 CONFIG_ESP_HOSTED_P4_DEV_BOARD_FUNC_BOARD=y가
   Function EV 보드 핀(CLK=33 CMD=4 D0=20 D1=23 D2=21 D3=22 RESET=53)으로
   자동 설정했다.
 - Nano 보드는 CLK/CMD/D0-D3/RESET = GPIO18/19/14/15/16/17/54.
   P4_DEV_BOARD_NONE=y로 바꾸고 핀을 직접 지정했다.
 - sdkconfig가 sdkconfig.defaults보다 우선하므로 두 파일 모두 고쳤다.
 - 증상: sdmmc_card_init failed 반복 -> esp_wifi_init failed: ESP_FAIL

6. esp-hosted 버전 불일치
 - host 3.0.7, C5 2.12.9로 메이저가 달라 호환 모드(RPC V2, streaming)로
   동작한다. 동작은 하지만 새 IDF/컴포넌트를 받으면 다시 어긋날 수 있다.
 - 저장소의 firmware/bin/ESP32-C5/esp32-c5-slave-260623.bin도 2.12.9라서
   플래시해도 mismatch는 해결되지 않는다.
   (Waveshare esp-hosted-mcu 2.12.x 기준, IDF v5.5.4, network_adapter)
 - 해결하려면 P4의 esp_hosted를 ~2.12.9로 고정하거나 C5를 3.x 슬레이브로
   직접 빌드해야 한다. 현재는 그대로 사용 중(Wi-Fi 정상).

7. 그 외
 - GCC 신버전이 stringop-truncation을 에러로 처리해서 esp-audio-player에만
   예외를 줬다. (CMakeLists.txt에서 -Wno-error=stringop-truncation)
 - spiffs/ 폴더는 git에 없으므로 클론 후 spiffs/music/을 만들어야 한다.
   (main/CMakeLists.txt:35의 spiffs_create_partition_image가 필요로 함)
 - SD카드를 꽂지 않으면 "Failed to mount SD card" 에러가 난다.
 - VideoPlayer는 SD카드의 /avi/ 폴더에서 MJPEG 코덱의 .avi 파일만 재생한다.
   mp4/H.264는 안 된다. 변환 예:
   ffmpeg -i in.mp4 -c:v mjpeg -q:v 3 -pix_fmt yuvj420p -c:a pcm_s16le -ar 44100 out.avi


== 빌드할 때 일반적으로 챙길 것 ==

 - IDF를 바꾸면 rm -rf build 할 것.
 - sdkconfig가 sdkconfig.defaults보다 우선하므로, 옵션을 바꿀 때는 둘 다 고치거나
   sdkconfig를 지우고 다시 생성해야 한다.
 - 새 IDF에서는 dependencies.lock이 다시 풀리면서 컴포넌트 버전이 바뀔 수 있으니,
   잘 되는 시점의 락 파일은 커밋해 둘 것.


== 정리 ==

오늘 문제 대부분은 rev3.1 자체가 아니라 IDF 스냅샷과 보드 핀 설정에서 왔다.
rev3.1만의 차이(카메라/ISP 쪽 하드웨어 기능)는 카메라를 써 보지 않아서
검증하지 못했다. 카메라 앱을 돌릴 때 다시 확인할 것.

확인된 동작: Wi-Fi(C5 경유), 이더넷(DHCP), SD카드, avi 동영상 재생.

== 카메라(OV5647) PPA 보정 (브랜치: camera-ppa-fix) ==

증상
 - HX8394 720x1280 portrait LCD에서 카메라를 정면으로 향해도 대상이 한참 옆으로
   치우쳐 보였다. (hardware xy_swap 없음)

원인 분석 (Camera.cpp / esp_cam_sensor 레지스터 분석)
 - 720x1280 요청은 "input width=720, height=1280 is not supported"로 실패하고
   800x1280 센서 모드로 폴백했다.
 - 800x1280 센서 모드(ov5647_mipi_2lane_24Minput_800x1280_raw8_50fps.h)는
   센서의 가로 2110 x 세로 1448 창(HSTA=512, VSTA=248)을 800x1280으로 내보낸다.
   -> 창 중심이 센서 중심보다 오른쪽으로 약 255px 치우쳐 있고,
      가로 약 2.6배 / 세로 약 1.1배로 비균등 압축된다.
   -> 원래 800x1280 패널(10.1인치 JD9365)에 맞춘 모드라 720x1280 패널에는 안 맞는다.
 - LCD-7B(1024x600 landscape)는 센서 landscape 프레임을 그대로 써서 문제가 없었다.
   (factory 설정은 확인하지 못함)

수정 내용
 - sdkconfig.defaults: landscape 1280x960 (RAW10 binning, 45fps) 모드를 켜고 기본으로 지정
   CONFIG_CAMERA_OV5647_MIPI_RAW10_1280X960_BINNING_45FPS=y
   CONFIG_CAMERA_OV5647_MIPI_DEFAULT_FMT_RAW10_1280X960_BINNING_45FPS=y
   (sdkconfig에도 FORMAT_INDEX_DEFAULT=4 로 반영)
 - Camera.cpp: 1280x960을 먼저 요청하고, 실패하면 800x1280으로 폴백.
   카메라 프레임과 패널의 방향이 다르면 PPA로 중앙 크롭 후 90도 회전
   (1280x960 중앙 1280x720 -> 720x1280, 스케일 1.0).
 - 조정 매크로 (Camera.cpp 상단)
     CAMERA_PPA_ROTATE_ANGLE  기본 PPA_SRM_ROTATION_ANGLE_90 (PPA 회전은 반시계 기준)
     CAMERA_PPA_MIRROR_X/Y    기본 0
     CAMERA_CROP_ZOOM         기본 1.0 (1 이상, 중앙 기준 확대)
     CAMERA_CROP_SHIFT_X/Y    크롭 창 이동(소스 프레임 픽셀, 회전 전 좌표)
   * 소스 x 방향(회전 후 화면 세로)은 1280 전체를 쓰므로 이동 여유가 없다.
     그 방향으로 옮기려면 ZOOM도 함께 올려야 한다. 소스 y 방향은 +-120px 여유.

결과
 - "Camera format: 1280x960" 로그로 새 모드 적용 확인.
 - 회전은 카메라를 손으로 90도 돌려 맞추면 되고, 상하좌우 반전은 없었다.
 - 광축 어긋남은 이전보다 훨씬 줄었다. 남은 어긋남은 160도 광각 모듈의
   렌즈 조립 오차이거나 왜곡 때문에 중앙 판단이 어려운 것일 수 있다(확정 못 함).
 - CAMERA_CROP_SHIFT_X=100 으로 좋아진 것 같으나 손으로 잡고 봐서 불확실하다.
   커밋된 값은 100. 나중에 카메라를 고정하고 격자/눈금 같은 대상으로 다시 맞출 것.

부수 발견: 카메라 케이블(FPC)을 뒤집어 꽂아 센서가 안 잡힌 적이 있다.
 (증상: "read pid_h failed", "Get sensor ID failed", "Failed to detect camera sensor")


== 병합 이미지 (0x0 기준) ==

 - 만들기 (build 디렉터리에서):
   esptool --chip esp32p4 merge-bin -o ../brookesia_firmware.bin @flash_args
 - 크기 0xF20000 (약 15.1MB), 16MB 플래시에 들어감. storage(5MB)는 고정 크기라
   mp3(spiffs/music/*.mp3 5개, 약 3.1MB)를 넣어도 이미지 크기는 변하지 않는다.
   SPIFFS 사용 가능 용량은 약 4.8MB.
 - 플래시: esptool --chip esp32p4 -p <포트> write-flash 0x0 brookesia_firmware.bin
 - 이전 FactoryOnly-260623.bin 과는 파티션 레이아웃이 달라 섞어 쓰면 안 된다.
 - 앱을 다시 빌드했으면 병합도 다시 할 것.

== 동영상 재생 (VideoPlayer) ==

 - SD카드의 /avi/ 폴더에서 MJPEG 코덱의 .avi만 재생한다 (mp4/H.264 불가).
 - 변환 예: ffmpeg -i birds.mp4 -c:v mjpeg -q:v 3 -pix_fmt yuvj420p \
                  -c:a pcm_s16le -ar 44100 birds.avi
 - birds.mp4(432x240, H.264) 변환본은 약 8.6MB. 재생 확인함(원본에 소리 없음).
 - 원본에 오디오(AAC)가 있으면 앱이 오디오를 재생하는지는 아직 확인하지 못했다.

이더넷도 확인함: 링크업 후 DHCP로 IP를 받음. 메모리 여유 SRAM 약 347KB, PSRAM 약 22.9MB.


== Face / Object Detection 조사 (조사만 함, 코드 없음) ==

현황
 - 이 저장소에는 얼굴/객체 검출 코드가 없다 (esp-dl, human_face_detect, yolo 등 검색 결과 없음,
   managed_components 와 dependencies.lock 에도 없음).
 - 카메라 관련 코드: Camera.cpp(프리뷰), 09_simple_video_server, 10_video_lcd_display.

공식 구성
 - esp-dl (v3.3.11): 추론 프레임워크(.espdl, 듀얼코어, PSRAM 메모리 계획).
   추가: idf.py add-dependency "espressif/esp-dl^3.3.11"
 - human_face_detect (v0.5.0): 얼굴 검출. 2단계(MSR+MNP) 또는 1단계(ESPDet-Pico 224/416).
   ESP32-S3, ESP32-P4 지원. 모델은 플래시 또는 SD카드에 둘 수 있다.
 - 그 외 모델: COCO 80클래스 검출(YOLO11n, YOLO26), 보행자, 손, 고양이/개, 손동작,
   얼굴 인식, 포즈 등 대부분 P4 지원.
 - esp-detection: 자체 데이터로 검출 모델을 학습해 esp-dl로 배포하는 도구.
 - ESP-WHO: esp-dl 위의 얼굴 검출/인식 응용 프레임워크.
 - P4 속도(esp-detection 문서): ESPDet-Pico 224x224 약 51ms(18fps 이상),
   160x288 약 46ms, 416x416 약 202ms. (입력 해상도 기준, 카메라 해상도가 아님)

이 프로젝트에 붙일 때 확인할 것
 1. IDF 6.1 호환: esp-dl 문서는 "release/v5.3 이상"이라고만 하고, 얼굴 검출 예제의
    검증 목록에는 IDF 5.3, 5.4만 나온다. 6.1에서 빌드되는지 확인하지 못했다. 가장 먼저 시험할 것.
 2. P4 rev3.x: esp-dl 쪽 호환은 확인하지 못했다. (이 프로젝트는 REV_MIN_301)
 3. 입력 포맷: 프리뷰는 RGB565, 모델 입력은 보통 RGB888 계열. esp-dl 이미지 유틸이
    RGB565를 직접 받는지 확인하지 못했다. 안 받으면 PPA로 변환+축소 단계가 필요.
 4. 화면 좌표: 프리뷰가 90도 회전과 크롭을 하므로 검출 박스 좌표 변환이 필요.
 5. 박스 그리기: 프리뷰는 LVGL을 멈추고 LCD 프레임버퍼에 직접 쓰는 구조(dummy draw)라
    프레임버퍼에 직접 그려야 한다. 추론은 별도 태스크로 돌려야 프리뷰가 안 끊긴다.

추천 순서(다음 작업, 새 브랜치에서)
 1. esp-dl + human_face_detect 를 의존성에 추가해 IDF 6.1 빌드가 되는지 확인
 2. 카메라 프레임을 PPA로 224x224 등으로 축소해 추론 태스크에 넘기는 최소 예제
 3. 검출 결과(박스)를 프리뷰 프레임버퍼에 그리기

## 추가 기록: VideoPlayer PPA 회전 (브랜치: videoplayer-ppa-rotate)
########################################################################

증상
 - 가로 영상(birds.avi, 432x240)을 재생하면 세로 패널(HX8394 720x1280)에서 폭에 맞춰
   위아래에 검은 띠를 두고 작게 나왔다.
   로그: "Scale video frame: 432x240 -> 720x400, offset 0,440"
 - 화면을 90도 돌려서 봐야 영상이 크게 똑바로 보이는 상황.

원인
 - VideoPlayer.cpp 가 회전 없이(PPA_SRM_ROTATION_ANGLE_0) 폭 기준으로만 스케일했다.

수정 내용 (components/VideoPlayer/VideoPlayer.cpp)
 - 영상과 패널의 방향이 다르면(가로 영상 + 세로 패널) PPA로 90도 회전한다.
 - 회전한 프레임을 비율을 유지한 채 패널에 최대한 크게 맞춘다.
   (432x240 -> 회전 후 240x432 -> 약 711x1280로 확대)
 - 방향이 같으면(세로 영상 + 세로 패널) 회전하지 않는다.
 - 회전 방향 매크로: VIDEO_PPA_ROTATE_ANGLE (기본 PPA_SRM_ROTATION_ANGLE_90, 반시계).
   기본값에서는 기기를 시계 방향으로 90도 돌려 보면 똑바로 보인다.
   반대로 보려면 PPA_SRM_ROTATION_ANGLE_270.

PPA 회전 시 스케일 규칙 (esp-idf esp_driver_ppa/src/ppa_srm.c:234-239)
 - 회전 0/180도: 출력 폭 = in.block_w * scale_x, 출력 높이 = in.block_h * scale_y
 - 회전 90/270도: 출력 폭 = in.block_h * scale_y, 출력 높이 = in.block_w * scale_x
   즉 scale_x/scale_y 는 회전 전 소스 축 기준이다. 90/270도에서는 scale_x 가 출력 높이에,
   scale_y 가 출력 폭에 적용된다. (Camera.cpp 의 크롭/회전도 같은 규칙을 따른다.)

같은 패턴
 - Camera.cpp 와 VideoPlayer.cpp 모두 "소스/패널 방향이 다르면 PPA 90도 회전 + 비율 유지 스케일"로
   처리한다. hardware xy_swap 이 없는 세로 MIPI-DSI 패널에서 쓰는 방법이다.

상태
 - 빌드 성공. 화면에서의 확인(꽉 차는지, 회전 방향)은 사용자가 보드에서 확인할 것.

== 하드웨어 조립 주의사항 (GND) ==

 - Nano 보드 + 5인치 HX8394 LCD + 라즈베리파이용 프로토타입 쉴드(드릴 가공)를 M2.5 나사로
   조립하면 세 보드의 GND 가 나사 구멍을 통해 연결될 수 있다.
 - GND 끼리 묶이는 것 자체는 원래 하나의 시스템이라 정상이다. LCD 구멍은 전원 GND 와 연결되어 있다.
   Nano 보드의 구멍이 GND 인지는 확인하지 못했다(회로도는 텍스트 추출로는 판독 불가).
 - 위험한 경우: 구멍/패드가 GND 가 아니라 5V/3.3V 등에 연결된 경우, 프로토타입 쉴드의 전원 레일이 구멍 근처에
   있는 경우, 드릴 가공으로 생긴 구리 조각/버가 인접 패드와 이어진 경우, 금속 스탠드오프가 다른 곳에 닿는 경우.
 - 점검(전원 OFF, 나사 조립 상태): 구멍-GND 도통, 5V-GND / 3.3V-GND 단락 여부, 나사 주변 패드 육안 확인.
   전원을 켠 뒤에는 5V 레일이 약 5V 인지, 뜨거운 부분이 없는지 확인.
 - 결과: GPIO-GND 단락 없음, 발열 없음, 지금까지 정상 동작. 재조립할 때 스탠드오프가
   다른 패드에 닿지 않는지만 다시 볼 것.


== PoE HAT 사용 시 주의사항 ==

 - 보드에 "PoE 모듈 전원 / 외부 5V 입력" 커넥터와 PoE 모듈 커넥터가 있다. RJ45 는 PoE 지원 자석(HBJ-6117ANL).
 - 문서/회로도로는 USB 5V 와 PoE 5V 사이의 전원 선택(ORing)이 있는지 확인하지 못했다.
   같은 Waveshare 의 ESP32-P4-ETH 는 USB 와 PoE 동시 사용이 가능하다고 하고, ESP32-S3 ETH POE 는
   동시 연결 금지 경고가 있다. Nano 는 알 수 없다.
 - 위험: ORing 이 없으면 두 5V 가 맞물려 PoE 전압이 USB(PC 포트)로 역류하거나, 반대로 USB 5V 가
   PoE 모듈 출력으로 들어가 PC USB 포트나 PoE 모듈이 손상될 수 있다.
 - 확인 방법(동시에 꽂기 전에 멀티미터로):
     1) PoE 만 연결, USB 는 뺀 상태에서 USB-C 커넥터 VBUS 전압 측정: 약 5V 면 역류 구조 -> PoE 를 켠 채
        PC 를 연결하면 안 됨. 0V 근처면 격리됨.
     2) USB 만 연결, PoE 랜선은 뺀 상태에서 PoE 모듈 커넥터의 5V 핀 전압 측정: 5V 가 나오면 USB 5V 가
        PoE 모듈 쪽으로 들어가는 구조.
 - 동시에 꽂아 봤는데 이상은 없었다. 그러나 그것만으로 격리가 있다고 단정할 수 없어서
   둘 중 하나만 쓰기로 했다: 개발할 때는 USB, 단독 동작 때는 PoE.
 - PoE 를 쓰면서 시리얼 로그만 보려면 VBUS 를 차단한 USB 데이터 전용 케이블을 쓰는 방법이 있다.

## 추가 기록 (2026-09-22): 시간대(KST) / 이더넷 시간 동기화 / NTP 서버 (브랜치: timezone-fix)

증상
 - Settings 앱에서 Wi-Fi 를 연결하면 잠시 뒤 메인 화면 상단 시계가 맞춰지는데 한 시간 느리게 표시됨.
 - 이더넷만 연결했을 때는 시각이 맞춰지지 않음.

원인 (components/Settings/Settings.cpp)
 - SNTP 동기화가 끝나면 time_sync_notification_cb 에서 setenv("TZ", "CST-8", 1) 를 호출한다.
   CST-8 은 중국 표준시(UTC+8). 한국(KST)은 UTC+9 라서 한 시간 느리게 나왔다.
   (Waveshare 예제가 중국 기준으로 작성된 것으로 보임. NTP 서버는 UTC 시간만 주므로 시간대 문자열이 원인.)
 - SNTP 시작을 IP_EVENT_STA_GOT_IP(Wi-Fi IP 획득) 이벤트에만 걸어 두었다.
   이더넷은 IP_EVENT_ETH_GOT_IP 라는 다른 이벤트를 써서 이더넷만 연결하면 SNTP 가 시작되지 않았다.

수정
 - TZ 를 "KST-9" 로 변경 (로그 메시지도 "timezone KST-9 applied").
 - wifi_time_event_handler 가 IP_EVENT_STA_GOT_IP 와 IP_EVENT_ETH_GOT_IP 둘 다 받아 SNTP 를 한 번만 시작.
   (start_time_sync_once 가 이미 시작됐으면 무시)
 - 핸들러 등록 직후 이더넷 netif("ETH_DEF")에 이미 IP 가 있으면 바로 시작
   (설정 앱이 등록되기 전에 이더넷이 먼저 IP 를 받는 경우 대비).
 - NTP 서버를 두 개로: 0번 kr.pool.ntp.org, 1번 time.google.com (기존 ntp.aliyun.com 제거).
   CONFIG_LWIP_SNTP_MAX_SERVERS 를 1 -> 2 로 올림. esp_sntp_setservername(idx, ...) 의 idx 가
   이 값 미만이어야 하므로 서버를 더 쓰려면 이 값도 올려야 한다(범위 1~16).
   sdkconfig 와 sdkconfig.defaults 둘 다 반영. (sdkconfig 가 우선)
 - SNTP 재동기화 주기: CONFIG_LWIP_SNTP_UPDATE_DELAY=3600000 (1시간).

결과
 - Wi-Fi, 이더넷 둘 다 시각 맞추기 정상. 한국 시각으로 표시됨.
 - 한쪽 NTP 서버가 응답하지 않을 때 다른 서버로 넘어가는 동작은 직접 막아 보며 확인하지는 않았다.
 - 시간대 설정은 동기화가 끝난 뒤에 적용된다. 동기화 전에는 UTC 기준으로 보일 수 있다.
